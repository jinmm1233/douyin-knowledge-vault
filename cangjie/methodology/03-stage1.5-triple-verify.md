# 阶段 1.5 — 三重验证（任务优先）

## 目标与适用范围

判断候选是否有依据、能执行、对任务有用；**是否独立成 Skill 留给阶段 1.6**。
思想型内容与工具书共用这三个目标，但按候选类型选择证据和测试方式。一本书可以混合多种类型。

旧判据把跨语境重复、外推新颖性、作者独特性当成全部候选的硬门槛，会误筛只在一处讲透的工具书机制。本版本不再按出现次数或反直觉程度一票否决；也不把“一处提到”当成充分证据。

## 三重验证（verified 需全部通过）

### V1 — 来源充分性（Source Sufficiency）

**问题：可定位的原文，是否足以支持这个候选在限定范围内的内容？**

| 候选类型 | 核查重点 |
|---|---|
| framework / principle | 原文是否明确提出或足以重建该规则；解释是否越过原文支持范围 |
| procedure / calculation / troubleshooting | 适用条件、必要输入、步骤/公式/判断分支和输出是否完整；引用涉及的图表、脚注、单位有没有漏读 |
| case / counter-example / term | 作为支持材料或参考保留；若要升级为能力，须另有可执行规则支持 |

- **一处完整说明可以通过**。只有名称、口号、半条公式或缺少关键条件，不能据此补出完整方法。
- 多语境是辅助支持，不是数量门槛。相同案例的重复转述不算新的独立证据；不同章节也不自动意味着证据独立。
- 记录 `source_id`、版本（可得时）和章节/页码/时间戳/chunk_id 等可回查位置。引用与规则逐项对应，不能只有书名。
- 一处公式与另一处单位说明可以合读，不要求每处都单独讲透。存在冲突时保留冲突及定位，未解决之前转 `needs_review`。
- 区分“忠实于原文”与“现实中已被证实有效”。原文的假设、时效、作者立场要进入 B；不要借一次引用宣称普适可靠。

### V2 — 可执行性（Executability）

**问题：换一组合法输入，能否按这个方法完成一个明确任务，并检验结果？**

- 思维框架：用一个适用范围内的新问题，检查分析步骤、决策依据和边界；不能只复述原句。
- 流程/计算/排障：使用同领域的新输入，检查步骤、分支、单位、输出和判停。**不要求跨领域迁移或新颖结论**。
- 先固定输入和完成标准，再做演练。计算型给出独立核对的预期数值/容差；流程型给出必要步骤、最终交付物和缺失输入处理。
- 演练不得补造原书没提供的关键规则。原书信息不足则转 `needs_review`；已完整但无法产生具体动作/结果则降为 `reference`。
- 阶段 1.5 的纸面演练记录为 `walkthrough`，不是实际宿主执行。阶段 4 必须另测真实输出，未做时不能声称“已实测”。

### V3 — 任务增益（Task Utility）

**问题：把这条内容固化后，能给目标任务带来什么具体帮助？**

至少说明一种可检查的价值，例如减少遗漏、统一指标口径、稳定交付格式、改善决策结构、识别失败边界、节省重复操作。阶段 4 用结果检验这一判断。

- 标准 SOP、普通公式、常见检查表只要有任务增益，就可以保留；不要求作者独创、反常识或模型“以前不知道”。
- 作者的独特视角可加分，但不能代替可执行性。
- “努力就好”之类无具体行为约束、无明确任务收益的句子保留为参考，不包装成能力。
- 不凭自评宣称比无 Skill 更好；记录待比较的收益，最终通过同任务基线评测核实。

## 判定与去向

| decision | 条件 | 保存及下游处理 |
|---|---|---|
| `verified` | V1/V2/V3 均通过 | 写 `verified.md`，进入阶段 1.6；不等于自动成为独立入口 |
| `reference` | 有来源价值，但不是可独立执行的方法 | 记 `references.md`；阶段 3 写入 Bundle 的 `book/overview.md` 参考区或 `book/glossary.md`，审计中登记实际交付路径 |
| `needs_review` | 关键条件缺失、来源冲突、尚不能检验 | 记 `needs-review.md`，列具体缺口和补读/询问事项；不进入 active 能力池 |
| `rejected` | 无原文依据、错误归因，或去重后被另一候选完整覆盖 | 写 `rejected/<id>.md`，附理由；重复项注明保留的 canonical ID |

重要但待核查的内容不能静默消失；没有完成参考映射也不能声称“知识已保留”。重要缺口尚未处理时，交付标记为部分完成并向用户说明。用户确认只确认范围，不能替代来源或执行验证。

## 执行流程

1. 合并五个 `candidates/*.md`，去重并保留所有出处和原候选 ID。
2. 按候选标注类型，不把整本工具书里的思想段落都当 SOP，也不把所有命名机制都当术语。
3. 逐项核查 V1/V2/V3，写依据、演练结果和 decision；不为达到“正常通过率”淘汰或凑数。
4. 对照阶段 0 的原书任务清单，写 `coverage-audit.md`：任务 → 原文位置 → 候选 → decision → 最终去向。旧版没通过的候选也纳入核查。
5. 对 `critical/high` 任务逐项复核，无对应候选则补读提取；信息不足明确记为缺口，不虚报零遗漏。
6. **用户轻确认**：展示可执行候选、参考、待核查、淘汰四类及重要缺口。确认后进入阶段 1.6，而不是承诺“这 N 个都会独立成 Skill”。

若没有任何 verified 候选，不为满足输出数量而凑 Skill；说明原因，交付参考/缺口清单并停止编译。

## 旧结果如何补审

- 不批量覆盖旧产物。读取原文、原候选和 rejected 理由，优先补审“仅因语境不足/不独特/无作者亲历案例”被筛掉的重要内容。
- 有原始记录就沿用候选 ID，并保存旧判定与新理由；旧 `V1_cross_domain` 等字段是历史记录，不自动等价于新三关通过。
- 新入选内容走阶段 1.6–4 后再编译，沿用用户已有 single/pack 选择。不为补回内容自动增加独立入口。
- 仅有群友描述、没有原文时，记录待取得材料；不能凭方法名称重建规则或宣布已修复该本书。
